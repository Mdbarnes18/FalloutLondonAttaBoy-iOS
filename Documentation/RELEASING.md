# Release process

## Development and release source

The canonical development branch is **`main`**. Repository changes are committed directly to `main`; do not create feature branches or use pull requests for this project's normal development workflow. The four platform build workflows run on pushes to `main`.

## Coordinated release gate

A numbered GitHub Release is published automatically after all four platform workflows succeed for the **same `main` commit SHA**:

1. The release workflow checks for successful iOS, Android, Windows and Linux build runs for that exact SHA.
2. It downloads the platform artifacts produced by those runs.
3. It verifies that exactly one package of each expected type is present.
4. It normalizes the eight installable package names using the root `VERSION` file.
5. It generates a SHA-256 checksum file for the eight packages.
6. It writes project-authored release notes describing downloads, capabilities, installation requirements, known limitations and source revision.
7. It publishes one combined GitHub Release.

The release notes do not include an autogenerated contributor list. Legal notices, upstream license obligations and required attribution are retained. A version that already exists is not silently overwritten.

If a platform build fails, is missing, or does not have an artifact matching the expected package type, the coordinated release must not be published.

## Versioning

- The format is `major.minor` with a two-digit minor component (for example `1.00`, `1.01`, `1.10`).
- The previous release history was cleared; the clean release line begins at **1.00**.
- The root `VERSION` file is the source of truth.
- Bump `VERSION` directly on `main` when intentionally preparing a new release.
- Do not reuse a published version. The release workflow refuses to overwrite an existing tag/release.

## Published package names

For version `X.YY`, the release contains:

- `Fallout-London-Companion-X.YY-iOS-unsigned.ipa`
- `Fallout-London-Companion-X.YY-Android.apk`
- `Fallout-London-Companion-X.YY-Windows-Installer.msi`
- `Fallout-London-Companion-X.YY-Windows-Portable.exe`
- `Fallout-London-Companion-X.YY-Linux-x86_64.AppImage`
- `Fallout-London-Companion-X.YY-Linux-amd64.deb`
- `Fallout-London-Companion-X.YY-Linux-x86_64.rpm`
- `Fallout-London-Companion-X.YY-Linux.flatpak`
- `SHA256SUMS-X.YY.txt`

The IPA is unsigned and requires a compatible signing/sideloading workflow. The Android APK is a debug build, not a Play Store production package.

## Build validation and release checklist

Before relying on a release:

- Confirm all four platform build workflows are green for the same `main` commit.
- Confirm the iOS simulator test result specifically. At present, the iOS workflow's simulator-test step is configured with `continue-on-error: true`; therefore, a green IPA workflow alone does **not** prove that the simulator tests passed.
- Confirm the release contains all eight installable packages and the checksum file.
- Check that the release notes' known-limitations section still matches [README → Status](../README.md#status-what-works-and-what-is-unverified).
- Remember that CI build/package success is not proof of live Fallout: London session compatibility.
